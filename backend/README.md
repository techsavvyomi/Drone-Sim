# PlutoSim: profiles & analytics backend (prototype)

User activation, pilot profiles, flight-session telemetry and admin analytics,
stored in Google Sheets behind a Google Apps Script web app.

```
PlutoSim (renderer)                        UserService / SessionService / AnalyticsService
        │  IPC (window.api.account / .telemetry)
        ▼
Electron main process                      token storage, offline outbox, HTTPS transport
        │  HTTPS POST, JSON
        ▼
Google Apps Script web app                 backend/apps-script/*.js  (validation, rules, IDs)
        │
        ▼
Google Sheets  "DroneSimulatorDB"          Users, ActivationKeys, FlightSessions, ...
```

The simulator never touches the spreadsheet. The API contract in
`src/shared/backend/contract.ts` is the part meant to outlive the prototype:
moving to Firebase replaces the Apps Script and the transport in
`src/main/backend/transport.ts`, not the game.

- Spreadsheet: https://docs.google.com/spreadsheets/d/19q9iUHRDD6MPORsL98WOGi6GtxQ4-b4m1l9THFUg-S0/edit
- Web app: https://script.google.com/macros/s/AKfycbwwK87DaHuCRxWm09UJOw0Bd7uetYVUU5HpuOneXajS5zpYA_Uv2i30bnjAZmJeoAgX/exec

## 1. Deploy

The whole backend is one generated file, **`backend/dist/DroneSimulatorAPI.gs`**.

1. Open the Apps Script project behind the web app URL above (script.google.com,
   or in the spreadsheet: **Extensions → Apps Script** if the script is bound to it).
2. Replace everything in `Code.gs` with the contents of `backend/dist/DroneSimulatorAPI.gs`.
   Delete any other `.gs` files from earlier experiments.
3. **Project Settings → Show "appsscript.json" manifest file in editor**, then replace
   `appsscript.json` with `backend/apps-script/appsscript.json`. It sets the V8 runtime,
   the time zone, and web app access (**Execute as: Me**, **Who has access: Anyone**).
4. Select **`setupDatabase`** in the function dropdown and press **Run**. Approve the
   permissions prompt. This creates every sheet, header, catalog row and setting, and is
   safe to run again at any time.
5. Run **`generateTenActivationKeys`**. Ten new keys appear in the `ActivationKeys` sheet
   (and in the execution log).
6. Redeploy **without changing the URL**: **Deploy → Manage deployments → ✏️ Edit →
   Version: New version → Deploy**. (Deploy → *New deployment* creates a new URL, which
   then has to go in `src/main/backend/config.ts`.)
7. Check it: open the web app URL in a browser. It should return
   `{"success":true,"data":{"service":"plutosim-api","apiVersion":1}}`.
8. Optional: run **`installAnalyticsTrigger`** so the report sheets refresh hourly, and
   **`refreshAnalytics`** to build them now.

The script's owner needs edit access to the spreadsheet. The spreadsheet ID is
`DEFAULT_SPREADSHEET_ID` in `Db.js`. To point a copy of the script at a test sheet,
set a `SPREADSHEET_ID` Script Property instead of editing the code.

**After changing any file in `backend/apps-script/`:** run `npm run build:apps-script`,
paste the new bundle, and redeploy a new version (step 6). `npm test` fails while the
bundle is stale.

### Admin tasks

| Task | How |
| --- | --- |
| Issue keys | Run `generateTenActivationKeys`, or use the **PlutoSim → Generate activation keys…** menu (shown when the script is bound to the sheet). |
| Disable a key | Set its `Status` to `DISABLED` in `ActivationKeys`. |
| Fix users typed into the sheet by hand | Run `repairUsers`. It links their keys, fills blank columns and moves the ID counter past them. |
| Deactivate a user | Set their `Status` to `INACTIVE` in `Users`. |
| Sign out a device | Set the row's `Status` to `REVOKED` in `AuthTokens`. |
| Free a profile for another computer | Clear `Device ID` and `Device Name` in `Users`. Pilots normally do this themselves with **Sign out of all devices**. |
| Change point rules | Edit `Value` in `Settings`. Takes effect on the next request. |
| Retire a drone / mission | Set its `Status` to `INACTIVE`. New sessions with it are refused. |

Do not put formulas inside the data sheets: rows are rewritten whole. Build ad-hoc
analysis in separate sheets or pivot tables.

### Pointing the simulator somewhere else

`src/main/backend/config.ts` holds the prototype URL. `DRONESIM_BACKEND_URL` overrides it
at run time (`DRONESIM_BACKEND_URL=https://… npm start`) or at build time; `off` disables
profiles. With profiles on, the simulator opens on the activation screen.

## 2. Sheets (tables)

All IDs are generated by the server under a script lock. Counters live in `Settings`
(`SEQ_USER`, `SEQ_SESSION`, `SEQ_EVENT`).

| Sheet | One row per | Key | Firebase collection |
| --- | --- | --- | --- |
| `Users` | pilot | `User ID` (`USR-000001`) | `users` |
| `ActivationKeys` | key | `Activation Key` (`PLUTO-SIM-7K2P-X9MQ`) | `activationKeys` |
| `AuthTokens` | sign-in (at most one `ACTIVE` per user) | `Token Hash` | Firebase Auth (replaced) |
| `FlightSessions` | training, mission or free-flight session | `Session ID` (`SES-000001`) | `flightSessions` |
| `GameplayEvents` | event | `Event ID` (`EVT-000001`) | `gameplayEvents` |
| `Drones` | drone | `Drone ID` (`DRONE-001`) | `drones` |
| `Missions` | mission | `Mission ID` (`MISSION-001`) | `missions` |
| `TrainingModules` | Flight School module | `Training ID` (`TRAINING-001`) | `trainingModules` |
| `Settings` | rule or counter | `Key` | remote config |
| `CrashReports` | crash | `Report ID` (`CRS-000001`) | Crashlytics / `crashReports` |
| `Report: …` | generated analytics | — | BigQuery / dashboards |

Columns are addressed by header name, so they can be reordered or added to. Durations
and flight times are **seconds**; timestamps are real date-times.

**Users**: identity, status, and running totals (`Total Points`, `Total Flights`,
`Total Flight Time`, per-type counts, `Missions Completed`, `Training Completed`,
`Free Flight Time`, `Crash Count`, `Current Level`). Totals are maintained by
`endSession`. They can always be recomputed from `FlightSessions`, which is the record.

**ActivationKeys**: `AVAILABLE` → `ACTIVATED` (with `Assigned Email`, `User ID`,
`Activated Date`) or `DISABLED`. An activated key is bound to its email permanently.

**FlightSessions**: the raw activity log. `Flight Type` (`TRAINING` / `MISSION` /
`FREE_FLIGHT`), mission or training module, drone, `Start Time` / `End Time`,
`Duration` (session length without pauses), `Flight Time` (airborne under the pilot's
control), `Score` / `Max Score` / `Score Percent`, `Stars`, `Points Earned`, `Success`
(`IN_PROGRESS` → `SUCCESS` / `FAILED` / `ABORTED`), `Attempts`, `Crash Count`,
`Collision Count`, `Distance` (m), `Max Altitude` (m), `Battery Used` (%),
`Controls/Input Mode`, objectives, `Fail Reason`, `App Version`.

**GameplayEvents**: `Event Type`, `Event Data` (JSON), client `Timestamp`, and
`Received At`. Events recorded offline arrive late but keep their real time.

### What a session is

| Type | Starts | Ends |
| --- | --- | --- |
| `MISSION` | first *fly* after the briefing | completed (`SUCCESS`), or left (`FAILED` if the last attempt failed, else `ABORTED`). Retries are `Attempts` of the same session; flying again after completing is a new session. |
| `TRAINING` | first demo or practice of a module | module completed (`SUCCESS`), or left (`FAILED` / `ABORTED`). Every practice run is an attempt. |
| `FREE_FLIGHT` | first arm in the Fly view | leaving the Fly view or changing drone (`SUCCESS`; `ABORTED` if it never left the ground). |

A briefing read and closed, or a Fly view visited without arming, is not recorded.
The scripted demonstration in a lesson counts toward duration, never toward flight time.

### Events emitted

`MISSION_STARTED`, `MISSION_RESTARTED`, `MISSION_FAILED` (reason), `MISSION_COMPLETED`,
`CHECKPOINT_REACHED`, `PACKAGE_COLLECTED`, `ZONE_REACHED`, `PACKAGE_DELIVERED`,
`TARGET_DETECTED`, `TRAINING_STARTED`, `TRAINING_DEMO_STARTED`,
`TRAINING_ATTEMPT_STARTED`, `TRAINING_ATTEMPT_FAILED`, `TRAINING_COMPLETED`,
`FREE_FLIGHT_STARTED`, `FREE_FLIGHT_ENDED`, `DRONE_ARMED`, `DRONE_TOOK_OFF`,
`DRONE_LANDED`, `DRONE_CRASHED` (impact speed, altitude), `DRONE_RESET`, `BATTERY_LOW`,
`DRONE_CHANGED`, `CONTROLLER_CONNECTED`, `CONTROLLER_DISCONNECTED`, `SESSION_RECOVERED`.
The server accepts any `UPPER_SNAKE_CASE` type, so new events need no backend change.

## 3. API

`POST` to the web app URL with a `text/plain` body:

```json
{ "apiVersion": 1, "action": "startSession", "payload": { … }, "authToken": "…" }
```

Every response is HTTP 200 with an envelope:

```json
{ "success": true, "data": { … } }
{ "success": false, "code": "KEY_ALREADY_USED", "message": "…" }
```

`GET` returns a health check. Types for every request and response are in
`src/shared/backend/contract.ts`.

| Action | Auth | Payload | Returns |
| --- | --- | --- | --- |
| `activateUser` | — | `name`, `email`, `activationKey`, `deviceId`, `deviceName`, `signOutOtherDevices?` | `userId`, `authToken`, `profile`, `existingUser?` |
| `loginUser` | — | `email`, `activationKey`, `deviceId`, `deviceName`, `signOutOtherDevices?` | `userId`, `authToken`, `profile` |
| `signOut` | token | — | `signedOut` (the token is revoked) |
| `getUserProfile` | token | `userId` | profile + stats |
| `getUserDashboard` | token | `userId`, `recentLimit?`, `days?` | profile, recent sessions, daily series, mission / training / drone breakdowns |
| `startSession` | token | `userId`, `flightType`, `droneId`, `missionId?`, `trainingId?`, `inputMode`, `startTime`, `clientSessionKey` | `sessionId` |
| `endSession` | token | `sessionId`, `endTime`, `duration`, `flightTime`, `result`, `score`, `stars?`, `crashCount`, `attempts`, `distance?`, `maxAltitude?`, `batteryUsed?`, … | `pointsEarned`, updated `profile` |
| `recordEvent` | token | `sessionId?`, `eventType`, `eventData?`, `timestamp` | `eventIds` |
| `recordEvents` | token | `sessionId?`, `events[]` (≤ 100) | `eventIds` |
| `reportCrashes` | token optional | `reports[]` (≤ 20): `kind`, `message`, `stack?`, `fatal`, `occurredAt`, app / OS / device details, `context?` | `reportIds` |

Error codes: `VALIDATION`, `KEY_NOT_FOUND`, `KEY_ALREADY_USED`, `KEY_DISABLED`,
`EMAIL_ALREADY_REGISTERED`, `INVALID_CREDENTIALS`, `SIGNED_IN_ELSEWHERE` (with
`deviceName`), `USER_INACTIVE`, `AUTH_INVALID`, `NOT_FOUND`, `FORBIDDEN`,
`UNKNOWN_ACTION`, `SERVER_ERROR`.

### Security rules the server enforces

- **Keys.** A key must exist and be `AVAILABLE` to activate. Once `ACTIVATED` it only
  ever signs in its own email; any other email gets `KEY_ALREADY_USED`. One account per
  email.
- **Identity** comes from the `authToken` (issued at activation or login, stored only as
  a SHA-256 hash), never from a `userId` in the payload. A `userId` that is not the
  caller's own is `FORBIDDEN`, and so is a session that belongs to someone else.
- **Totals are the server's arithmetic.** `pointsEarned` from a client is ignored.
  Points and levels are computed from the result, the score and the stars using the
  `Settings` rules. Scores are clamped to the mission's `Max Score`, flight time to the
  duration, and the duration to the time between the session's start and end.
- **Catalog.** Drone, mission and training IDs must exist and be `ACTIVE`.
- **Idempotency.** A retried `startSession` with the same `clientSessionKey` returns the
  same session. A second `endSession` changes nothing.
- **One computer at a time.** A profile is bound to the computer it last signed in on
  (`Device ID` / `Device Name` / `Device Bound At` in `Users`). Signing in anywhere else
  while that computer still has an `ACTIVE` token gets `SIGNED_IN_ELSEWHERE`, naming
  it; the app asks "Sign out of all devices" and sends the sign-in again with
  `signOutOtherDevices`. Once that computer has signed out, another one moves in
  without being asked. Every sign-in revokes the profile's other tokens, and a token for
  a computer the profile is no longer bound to is refused (`AUTH_INVALID`, saying where
  the profile went). The app checks every 30 seconds while open, so a computer signed
  out this way finds out within a minute; a flight in progress finishes first.
- **Brute force.** 10 failed activations or logins per email lock that email for 15 minutes.
- **Formula injection.** Text that would be read as a formula (`=`, `+`, `-`, `@`) is
  stored as plain text.

It is still a prototype: the activation key is effectively a password that cannot be
changed, and anyone with the URL can call the public actions. Production auth is
Firebase's job.

### Points (defaults, editable in `Settings`)

| Session | Points |
| --- | --- |
| Mission completed | 50 + 25 per star + 10 per score point |
| Training module completed | 30 + 25 per star |
| Re-completing the same mission or module | 25% of the above |
| Free flight | 2 per full airborne minute, max 30 per session |
| Failed or aborted mission / training | 0 |

Level = 1 + floor(total points / 500).

## 4. Analytics

**In the simulator:** the **Profile** screen (top-bar chip, the pilot badge, or the
nav rail) shows the pilot's career: level, points, flight time, mission completion
rate, Flight School mastery, flight time and crashes per drone, 30-day charts and a
flight log. It is one `getUserDashboard` call.

**In the spreadsheet:** `refreshAnalytics` writes these report sheets, each with its
charts:

| Report | Answers |
| --- | --- |
| `Report: Overview` | registered and active users; pilots who flew today / 7 / 30 days; sessions and flight hours; key stock; sessions, active pilots, flight hours and points per day for 30 days |
| `Report: Users` | per pilot: points, level, sessions, flight time, missions and training completed, free-flight time, average score, crashes, last active |
| `Report: Missions` | per mission: sessions, pilots, attempts, average attempts, completion rate, average score, average duration, crashes, failures and the most common failure |
| `Report: Training` | per module: the same, for Flight School |
| `Report: Drones` | per drone: sessions, pilots, flight hours, missions completed, average score, crashes, crash rate |
| `Report: Crashes` | app crash reports in the last 24 h / 7 days, fatal ones, devices affected, reports by kind and per day, and **issues** grouped by fingerprint with first/last seen and latest app version |

The raw `FlightSessions` and `GameplayEvents` sheets remain the source for anything the
reports do not cover (pivot tables, exports, a later move to BigQuery).

## 5. Client behaviour

- **Offline-first telemetry.** Sessions and events go to a queue on disk
  (`telemetry-outbox.json` in the app's user-data folder) and are sent in order in the
  background, retrying with backoff. Nothing waits on the network to fly.
- **Crash-safe sessions.** An open session is checkpointed every 15 s. If the app is
  closed mid-flight, the next launch closes it as `ABORTED` with the last numbers and a
  `SESSION_RECOVERED` event.
- **Token storage.** The auth token stays in the main process, encrypted with the OS
  keychain (`safeStorage`), in `account.json`. The renderer never sees it.
- **Account switching.** Queued data is sent with the token of the user who flew it,
  even after they sign out.

## 6. Crash reports

The simulator reports every way it can go down. Reports are **not** in-game drone
crashes (those are `DRONE_CRASHED` events); they are the app itself failing.

| Kind | What happened | App behaviour |
| --- | --- | --- |
| `RENDERER_EXCEPTION`, `RENDERER_REJECTION` | uncaught JavaScript error in the game window | keeps running |
| `RENDER_ERROR` | a screen failed to render | the 3D view shows *Retry*; anything else shows a *Something went wrong / Reload* screen |
| `WEBGL_CONTEXT_LOST` | the GPU dropped the 3D context | keeps running |
| `RENDERER_GONE` | the game window's process crashed or ran out of memory | open flight session closed as `ABORTED`, window reloads (3 times in 2 minutes at most, then a message) |
| `CHILD_PROCESS_GONE` | the GPU or another helper process died | Electron restarts it |
| `MAIN_EXCEPTION`, `MAIN_REJECTION` | error in the Electron main process | keeps running |
| `NATIVE_CRASH` | hard crash; a minidump was written to the app's `Crashpad` folder | reported on the next launch (the dump itself stays on the computer) |

- Each report carries the app version, OS, device, the signed-in pilot (if any), a
  scrubbed stack trace (the user's home folder becomes `~`), and **context**: screen,
  mission or lesson and its phase, drone, map, graphics preset, camera, armed state,
  frame rate, draw calls, window size. `Context` is JSON in the sheet.
- Reports are queued on disk like flight data and sent even when nobody is signed in.
- The server fingerprints each report (kind + message with numbers and quoted values
  blanked + top stack frame without line numbers), so `Report: Crashes` lists one
  issue per fault however many times it fired.
- Floods are capped three times: the window sends an identical error once per 5 s, the
  app once per minute and 50 per run, and the server accepts
  `MAX_CRASH_REPORTS_PER_HOUR` (default 60) per device.

## 7. Moving to Firebase

| Prototype | Firebase |
| --- | --- |
| Sheets tables | Firestore collections with the same names (camelCase), document ID = the row ID |
| `AuthTokens` + email/key login | Firebase Auth; activation becomes a callable function that binds a key to `auth.uid` |
| `Api.js` handlers | Cloud Functions with the same action names and payloads |
| Script lock + `SEQ_*` counters | Firestore transactions (or keep the readable IDs through a counter document) |
| `Report: …` sheets | scheduled function → BigQuery / Looker Studio |
| `src/main/backend/transport.ts` | calls the functions instead of the web app |

The contract (`src/shared/backend/contract.ts`), the renderer services and the telemetry
tracker stay as they are.

## 8. Development

- `backend/apps-script/*.js`: the backend source, one concern per file.
- `npm test` runs it in Node over an in-memory spreadsheet (`tests/helpers/appsScript.ts`):
  `tests/backend-api.test.ts` (rules), `tests/backend-catalog.test.ts` (game ↔ catalog),
  `tests/backend-bundle.test.ts` (bundle is current), `tests/telemetry-outbox.test.ts`
  (queue), `tests/telemetry-sessions.test.ts` (what a flight records),
  `tests/crash-reports.test.ts` (scrubbing, throttling, window listeners).
- Adding a drone, mission or lesson: give it the next ID in both
  `src/renderer/services/catalog.ts` and `backend/apps-script/Catalog.js`, rebuild the
  bundle, redeploy, and run `setupDatabase` (it adds only the new rows).
